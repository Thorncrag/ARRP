# Project Consistency Audits

## Authority, Loading, and Dependencies

**Authority.** This module is authoritative for the scope, safeguards, deterministic baseline, and closeout of a non-tier, non-scoring Project Consistency Audit.

**Load when.** Load this module for a project-wide structural or integration review, when running or interpreting the project-consistency script, when a Change Audit begins with project-level consistency, or when a recurring integrity defect is being converted into a validation rule.

**Dependencies.** Load the [Framework kernel](../FRAMEWORK.md), [Audit Core](AUDIT_CORE.md), and [GitHub Workflow](../GITHUB_WORKFLOW.md). Load [Change Audits](CHANGE_AUDITS.md) when a consistency finding arises from or affects a governing change. External-source availability remains governed by the source-link audit rather than this module.

## Project Consistency Audit

A **Project Consistency Audit** is a non-tier, non-scoring review of cross-project structure and integration. It may check and mechanically correct file paths, front matter, identifier alignment, heading levels, required-section order, navigation, registries, source numbering, audit-history nomenclature, public-site boundaries, internal project links throughout the active repository, internal repository links embedded in GitHub issue bodies, and drift between an already-authoritative repository record and GitHub Project fields. It does not increment **Runs**. Run [`audit_project_consistency.py`](../../scripts/audit_project_consistency.py) as the repeatable structural and reader-language baseline, including its authenticated-host GitHub Issue and Project synchronization checks, then investigate and resolve or route every reported finding; run the ordinary test suite and public-site preparation as complementary validation. The encoded floor also checks Markdown heading anchors; area `issue_count`, active-list placement, canonical labels, and links; issue, audit, legislation, topic-guide, source-catalog, print-assignment, and print-assembly metadata; reciprocal issue-to-legislation routing; lifecycle-field coherence and required workflow explanations; front-door discovery routes; structured JSON and CSV validity; and common tracked-file or local-path artifacts. The internal-link pass covers all active project Markdown and HTML plus main-branch ARRP repository URLs stored in active project text records; generated build output and superseded archival snapshots are excluded. If GitHub cannot be queried, treat that portion as unverified and rerun it in the authenticated host context rather than treating the repository-only pass as complete. External-source availability is not part of this structural check and should be assessed under a distinct source-link audit so access controls, moved publications, and bot blocking are not misclassified as internal defects.

The scheduled **Project Integrity Bot** runs this same repeatable floor daily at approximately 1:35 a.m. EDT / 12:35 a.m. EST and after every push to `main`. It uses the configured Project credential to compare repository issue metadata against the issue registry, live GitHub Issues, and controlled GitHub Project fields; a missing credential fails the scheduled run instead of silently treating that surface as verified. It publishes a structured current report plus bounded run history to the data-only `project-console-data` branch and overwrites [`logs/PROJECT_INTEGRITY_REPORT.md`](../logs/PROJECT_INTEGRITY_REPORT.md) when the deterministic finding set, checked-page counts, or check scope changes. The Markdown file is a current snapshot, not a running audit ledger; timestamps and bounded history remain in the Console feed and GitHub Actions. The Integrity tab groups findings for repair; it is not a new audit tier, score, or license for automatic content changes. A clean automated result means only that the encoded checks found no defect. Codex or a human reviewer must still investigate problems outside the script's scope and improve the governing check when a newly verified recurring defect can be detected objectively.

The script is a required floor, not an exhaustive ceiling or a substitute for judgment. The auditor must follow credible signs of any other inconsistency, ambiguity, stale rule, weak cross-reference, reader-comprehension problem, implementation defect, or logical conflict found during the review; directly correct any convention-governed or already-supported defect, and route any legal, evidentiary, fiscal, remedial, lifecycle, or scoring judgment to the appropriate proposal-specific process. Absence of a script finding is never evidence that no other inconsistency exists. When a verified recurring finding can be objectively detected, improve the existing script or test suite so the next audit benefits from it; when the lesson is interpretive, incorporate it concisely into the governing file that owns the rule. Do not create another cumulative ledger for the pass: use `CURRENT_AUDIT.md` only while work is active, retain the user-facing closeout, preserve the committed change history, and let the bot-owned integrity report remain a replaceable current snapshot. Because the ordinary test suite and public-site preparation both rebuild the same staged artifact, run those two validations sequentially rather than concurrently.

A Project Consistency Audit may not alter an issue's diagnosis, evidence evaluation, remedy, legislative substance, lifecycle status, or score merely to make records appear uniform. A demonstrable transcription or synchronization error may be corrected to the existing authoritative record. Any finding that requires legal, evidentiary, fiscal, remedial, or scoring judgment must be routed to a proposal-specific Change Audit or the next appropriate T-audit.
