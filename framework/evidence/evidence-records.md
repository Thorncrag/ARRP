# Issue Evidence and Source-Development Records

## Authority and Dependencies

This file is the authoritative detailed rule for qualitative evidence placement and source-development records. Claim support belongs to [`annotation-and-source-standards.md`](annotation-and-source-standards.md), catalog ownership to [`../sources/source-catalogs.md`](../sources/source-catalogs.md), issue-level monitoring to [`../sources/project-monitoring.md`](../sources/project-monitoring.md), issue-page structure to [`../issues/issue-architecture.md`](../issues/issue-architecture.md), and physical placement to [`../PROJECT_STRUCTURE.md`](../PROJECT_STRUCTURE.md).

## Load When

Load this file when routing retained evidence to an issue or candidate; deciding whether evidence belongs on an issue page, a linked public evidence record, an internal source-development record, or a source-development stub; or reconciling source placement during substantive issue development or review.

## Evidence Architecture

1. **Proposal page.** The issue page remains authoritative for the institutional diagnosis, material manifestations, resulting damage, weakness, remedy, legislation, and conclusions. It should cite the strongest primary authority, controlling or material official findings, and representative evidence needed to establish each material proposition. A linked evidence record supplements but never excuses missing nearby citations for claims essential to the proposal.
2. **Issue evidence record.** Once the issue page already contains sufficiently strong evidence for its material propositions, place additional reader-useful evidence in a separate record when doing so preserves the issue page's clarity and concision. Create the reader-facing page at `areas/AREA/evidence/ISSUE-ID-evidence.md` using the [Issue Evidence Record Template](../templates/ISSUE_EVIDENCE_TEMPLATE.md). It may organize verified distinct episodes, primary instruments, judicial and official dispositions, corroborating sources, counterexamples, and defined monitoring items. It must not create an independent diagnosis, remedy, legislative proposal, score, status, or audit history. It links back to the canonical issue and cites sources registered in `sources.csv`. Reader-facing evidence records normally carry `public-proposal` print metadata; an edition may place selected records in an evidence appendix or omit them under its explicit export plan.
3. **Internal source-development record.** When routed sources are not yet appropriate for concise reader-facing prose, cite them in an issue- or candidate-specific internal source-development record. Proposal records live at `areas/<AREA>/research/<ISSUE-ID>-source-development.md`; formal Horizon records live at `research/horizon-source-records/<HOR-ID>-source-development.md`. The record states the candidate-specific proposition or verification question, review status, and monitoring qualification without treating the material as an adjudicated finding. A generic statement that the source concerns the described action, litigation, or episode is not sufficient; the entry must identify what institutional proposition, boundary, controlling action, or procedural question the later review is expected to resolve. It is an accountable use of the source and therefore places the source in `sources.csv`; it is not a substitute for later selecting the strongest evidence for the public proposal or evidence page.
4. **Source-development stub.** If an admitted or still-unresolved proposal identifier lacks a standalone page, create a print-excluded source-development stub using the project template. The stub owns and links the issue-specific source-development record but does not imply completed admission analysis, diagnosis, remedy, legislation, score, audit, or public-release readiness. It requires no audit sidecar until substantive proposal development begins.

The parent-issue monitoring rule is maintained in [`../sources/project-monitoring.md`](../sources/project-monitoring.md).

## Routing and Qualitative Placement

Unresolved routing leads belong in `sources-pending.csv` with the plausible competing destinations, the reason ownership cannot yet be selected, and the exact next routing decision. A pending row must not name one clear accountable owner; once an owner is clear, create or use that owner's source-development record and move the row to `sources.csv`. Temporary batch files may exist outside the repository while a scan is running, but the active tree must not retain a parallel source, litigation, integration, or routing ledger after reconciliation. Inclusion by a tracker or classifier does not make a lead public evidence.

The evidence-page decision is qualitative, not quantitative. There is no source-count or episode-count threshold, and neither a large intake nor an additional source automatically requires a separate reader-facing page. First ask whether the issue page already establishes each material proposition with sufficiently strong, representative evidence. A stronger or necessary new source belongs on the issue page, replacing weaker support where appropriate. Once the issue page is sufficiently evidenced, place additional material in a linked evidence record only when it has meaningful reader-facing value and the separate record improves clarity, organization, or continuing monitoring. Routed material that still warrants verification or later selection belongs in the internal source-development record, not `sources-pending.csv`. Cumulative corroboration adding no project value may be removed after a documented no-additional-value disposition.

For an automated large-intake review, each retained source routed to an existing issue must receive the same qualitative placement decision: issue-page integration when it strengthens necessary support; linked evidence-record integration when the issue page is already sufficiently supported and the additional material warrants reader-facing treatment; a proposition-bearing citation in the issue's internal source-development record when verification or later selection remains incomplete; or removal after a documented no-additional-value finding. Association with an identifier alone is not a citation and does not justify placement in `sources.csv`, but unfinished verification, monitoring, or issue development does not justify leaving a clearly routed source pending. When an evidence record exists, the canonical issue page should link it concisely from the end of **Manifestation of the Failure** as **Additional supporting record**. Do not add a generic administrative monitoring link, an administrative monitoring subsection, a missing-target placeholder, or monitoring boilerplate to a reader-facing proposal page.

Do not create a reader-facing evidence page merely to empty a queue. When the receiving issue is undeveloped or lacks a canonical issue page, create the internal source-development stub and its proposition-bearing source record instead of leaving clearly owned sources pending. When a formal Horizon candidate owns the material, its GitHub issue or linked candidate-specific source-development record supplies the citation; when a preliminary candidate owns it, the structured preliminary row's source identifiers and links supply the citation. Organize any public evidence page by institutional manifestation or mechanism rather than source order. Prefer prose headings and concise bullets over wide source tables that render poorly on mobile or in print.

## Source Reconciliation During Issue Work

At the start of substantive issue development or any T0-T4 or Change Audit, check its cited and source-development records and whether its parent GitHub issue carries `needs: monitoring`. A source awaiting verification remains associated with the issue in `sources.csv` and carries `Reviewed? = No`; a changing external record uses `Monitoring = Yes`; neither returns to pending unless later review genuinely makes ownership unclear. Initial development and T2-T4 work should verify sources, test route and remedy fit, select the strongest material for reader-facing integration, remove no-additional-value records, and preserve qualified or monitored source-development material without mistaking catalog placement for substantive integration.

Source reconciliation is part of the issue-development or audit work and does not create a separate T-audit run. Corroborating or cumulative-source placement that does not alter the issue theory requires no Change Audit. A source that materially changes a developed issue's manifestation, diagnosis, damage theory, remedy, proposal vehicle, or score basis triggers the ordinary Change Audit and Internal Remedy-Fit rules. At closeout, confirm that no clearly routed source remains pending, every pending row identifies competing destinations and an exact routing decision, any issue requiring continued review carries `needs: monitoring` on its existing GitHub issue, and any changing source that independently warrants recurring checks is marked `Yes` in `sources.csv`. Rebuild the ARRP Project Console whenever candidate data, either canonical source catalog, source-monitoring designation, issue-level monitoring label, presidential-directive registry, watcher configuration, a canonical project log, page-level publication-disposition metadata, or `framework/print-assembly.json` changes. Its progress, source, pending, watcher, integrity, log, and publication presentations are generated views, not separate tracking authorities.
